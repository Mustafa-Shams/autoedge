# DECISIONS — AutoEdge Storefront

Record of design decisions made during the storefront extension build (P30–P48).

---

## Decision Log

| # | Date | Phase | Question | Chosen Option | Rationale |
|---|---|---|---|---|---|
| 1 | 2026-11-08 | P30 | Storefront_seed.py location: `backend/database/` or `database/` at repo root? | `backend/database/storefront_seed.py` | Keeps seed alongside schema.sql and seed.sql; script needs backend imports and venv. |
| 2 | 2026-11-08 | P30 | Use separate SQLAlchemy model files or extend existing? | Separate model files per table, shared `__init__.py` | Follows existing codebase convention (one file per model). 25 model files total. |
| 3 | 2026-11-08 | P31 | Storefront framework: same Tailwind v3 as staff dashboard or v4? | Tailwind CSS v4 for storefront | Spec specifies new Vite project; v4 is the current version; no need to match staff dashboard. |

Both decoded by the same `jose.jwt.decode()` but different dependency functions check the scope. |
| 5 | 2026-11-10 | P34 | Vehicle catalog: query the `vehicles` table directly or use `v_vehicle_catalog` view? | Use view `v_vehicle_catalog` | Spec section 6.4 defines the view with joins for avg_rating and review_count. API reads from the view, writes go to the table. |
| 6 | 2026-11-12 | P36 | Bank account auto-creation: on signup or on first visit to bank page? | Auto-create on signup | Simpler UX — every customer always has a bank account and opening balance. No "setup" step needed. |
| 7 | 2026-11-12 | P37 | Reservation deposit: percentage from spec (`RESERVATION_DEPOSIT_PERCENT=10`) or let customer choose? | Fixed 10% from config | Spec section 9.1 is explicit: "10 % of `vehicles.price`". No customer choice. |
| 8 | 2026-11-12 | P37 | Lock order for reservation: vehicle → reservation → bank_account or different? | vehicle → reservation → bank_account | Per Article XIII of the constitution. All transactional routes follow this order. |
| 9 | 2026-11-14 | P38 | StockMovement.reference_id type: Integer or String? | Integer | Existing model uses `Integer` column. Reference IDs are reservation_id, sale_id, etc. |
| 10 | 2026-11-14 | P39 | Test drive expiry: cron job or checked on API access? | Checked on API access (expire_stale function) | No background worker needed; expiry is checked when test drives are listed or when a specific endpoint is called. |
| 11 | 2026-11-15 | P40 | Enquiry access: role-based or per-user flag? | Per-user `handles_enquiries` boolean on User model | Spec section 9.5 specifies this explicitly: "users.handles_enquiries = TRUE". Seed sets it for sarah and rita. |
| 12 | 2026-11-16 | P41 | Restock notification: email + in-app or in-app only? | Both email (if provider configured) + in-app notification | Spec section 9.6 says "notify every requester". Email via email_outbox, suppressed for @example.com domains. |
| 13 | 2026-11-16 | P42 | Review verified badge: how to determine? | Check if customer has a completed Sale for that vehicle | "Verified Buyer" badge appears when a Sale record exists for that customer + vehicle combination. |
| 14 | 2026-11-17 | P43 | Trade-in photo upload: Cloudinary direct or server-side? | Cloudinary direct (unsigned preset) | Spec section 9.7 and Manual Tasks section 17.1b. Keeps backend simple; frontend validates host. |
| 15 | 2026-11-17 | P44 | Service booking fee: from service_types.booking_fee or calculated? | From `service_types.booking_fee` | Spec section 9.8 defines booking_fee per service type. No calculation needed. |
| 16 | 2026-11-18 | P45 | Email provider: implement all three (Brevo, SendGrid, none) or just Brevo + none? | All three: Brevo, SendGrid, none | Spec section 10 defines the provider pattern. `none` logs only. Easy to add SendGrid alongside Brevo. |
| 17 | 2026-11-18 | P46 | Staff dashboard sidebar: where to add storefront management links? | Add Reservations and Staff nav items to sidebar | Staff need to see customer reservations, trade-ins, reviews, and service bookings from the dashboard. |
| 18 | 2026-11-20 | P47 | Ownership test responses: 403 Forbidden or 404 Not Found? | 404 Not Found | Spec section P47 explicitly says "404 not 403" — don't reveal that the resource exists to unauthorized users. |
| 19 | 2026-11-21 | Post-P48 | Increase showroom from 16 to 22 cars? | Yes — add 6 new vehicles (Fortuner, 488 GTB, C200, M4, 918, Swift) | Team decision: more variety (Coupe, Convertible, Diesel, Hybrid, budget). Photos added manually by teammates; `fetch_vehicle_images.py` skips them via `MANUAL_PHOTO_CARS` list. Colours may be changed later to match photos. |
| 20 | 2026-11-21 | Post-P48 | Should vehicle photos be loaded automatically from vehicle_images.json during seed? | No — photos added manually via staff portal vehicle form | Automatic photo matching mixed up different cars. `storefront_seed.py` no longer loads vehicle_images.json by default; opt-in with `--with-images` flag. `fetch_vehicle_images.py` is not called automatically anywhere. |
| 21 | 2026-11-21 | Post-P48 | Staff portal clarity: "Total Vehicles" KPI ambiguous (listings vs units) and vehicles page missing proper pagination | Disambiguate KPIs, add server-side paginated vehicle list | Dashboard: "Vehicle Listings" (count of rows = 22) + new "Units in Stock" card (sum of stock_quantity = 57). Backend `GET /api/v1/dashboard/stats` returns `units_in_stock`. `GET /api/v1/vehicles/` now returns `{items, total, skip, limit}` instead of a bare array. Vehicles page shows "Showing 1–10 of 22 vehicles", page-size selector (10/25/50), numbered page buttons, Prev/Next. Stock column kept. |
| 22 | 2026-11-21 | Post-P48 | All authenticated POST requests fail on live storefront + UX polish (bank card, notifications, compare/EMI/back buttons) | Fix trailing-slash 307 redirects, add bank card flip, unify notification count, fix compare/EMI/detail pages, add BackButton | **Root cause:** `@router.post("/")` on 5 store routes caused FastAPI 307 redirects that dropped the Authorization header in CORS cross-origin context → 401. Fixed to `@router.post("")` in reviews, enquiries, test_drives, trade_ins, restock. **Bank card:** 3D flip animation showing demo CVV "123" and "Use your login password" on back; eye toggle for full account number; new `GET /store/bank/sensitive` endpoint (owner-only). **Notifications:** New `NotificationContext` provides single `{unreadCount, refreshUnread}` consumed by Navbar + OverviewPage. **Compare:** Remove/Clear buttons now sync localStorage + URL; shows friendly empty state. **EMI:** Searchable vehicle dropdown from API + custom price option; supports `?vehicle=ID`. **Car detail:** Removed sticky overlap; added wishlist toggle; EMI link with vehicle ID. **BackButton:** Reusable component in both apps (navigate(-1) with fallback). 12 new backend tests (111 total). |
| 23 | 2026-11-21 | Post-P48 | Vehicle images: main image not shown first on storefront, last additional image lost, edit form doesn't load existing images | Add `PUT /vehicles/{id}/images/bulk` for atomic image replacement, include `images[]` in `VehicleResponse`, rewrite staff form image section, prepend `main_image_url` in storefront gallery | **Root causes:** (a) `CarDetailPage` passed `vehicle.images` (from `vehicle_images` table) to `ImageGallery` without prepending `main_image_url` — whatever had `sort_order=0` appeared first, not necessarily the main image. (b) Last image lost: mutation `onSuccess` called `navigate()` before the image POST loop finished (race condition). (c) Edit form showed "0/8" because `VehicleResponse` schema had no `images` field — `GET /vehicles/{id}` returned no images to populate the form. **Fixes:** Backend: added `VehicleImageResponse` and `BulkImageRequest` schemas with URL/limit/duplicate validation; added `images: List[VehicleImageResponse]` to `VehicleResponse`; new `PUT /vehicles/{id}/images/bulk` endpoint that atomically sets `main_image_url` + replaces all `vehicle_images` rows in one transaction. Staff form: complete rewrite of image section — loads existing images on edit, thumbnail previews, inline URL edit, delete with confirm, move up/down reorder, "Make main" swap, auto-adds pending URL on save, URL validation, max 8, uses bulk endpoint (no race). Storefront: `CarDetailPage` now prepends `main_image_url` as first gallery entry, deduplicating against `images[]`. Compare page confirmed correct (uses `main_image_url` for card). 17 new backend tests (128 total). |


| 24 | 2026-11-22 | A. Staff navigation | Why did staff pages lose navigation or crash on service creation? | Mount every staff page under one authenticated layout. Use the shared BackButton on detail and form views and place a route-scoped ErrorBoundary inside the layout. Service jobs use a dedicated options endpoint. | Navigation had to be mounted by each page. Enquiry pages passed header props the wrapper ignored. The service form called `.map()` on the new vehicle pagination envelope and fetched technicians from a manager-only endpoint. The new options endpoint serves vehicle, customer, and technician summaries to the service roles. |
| 25 | 2026-11-22 | B. Vehicles | What should Reserved mean for a multi-unit listing? | Owner selected any unexpired active reservation plus a Reserved: N badge. Apply word-based search, status filters, and stable sorting before pagination. | The frontend sent search as the make filter. Reserved previously looked only at vehicles.status. PostgreSQL's fn_sync_vehicle_status makes stock_quantity > 0 Available, zero stock with an active hold Reserved, and other zero stock Sold when stock changes. The listing reads the hold count separately and keeps the existing trigger. The default staff page size remains 10. Stock edits preserve zero, completed sales clear the last converted hold, and migration 0005 resynchronizes stale stored statuses through the existing trigger. |
| 26 | 2026-11-22 | C. Reservation expiry | How do overdue reservations close and refund? | Run a startup and three-minute sweep and commit lazy expiry before staff/store list, detail, and storefront creation. Lock vehicle, reservation, then bank account. Use shared close and refund logic. | Staff reads did not sweep. The worker waited 10 minutes before its first pass and acquired reservation locks before vehicle locks. The frontend treated elapsed deadlines as Expiring today. Each expiry updates the status, stock, 90% refund, both ledgers, and customer notification together. Rechecking status under a lock prevents repeated refunds. |
| 27 | 2026-11-22 | D. Customers | Can staff-created and legacy walk-in customers sign in? | Share account and demo bank provisioning with storefront signup, validate matching passwords, and let staff set a new password. Deactivation is manager-only. | Staff creation originally inserted only customers. Existing walk-ins lacked storefront credentials and bank rows. There was no customer lifecycle endpoint. Delete is restricted when sales, reservation, bank, or service history exists. Deactivation retains history and rejects storefront login and token use. |
| 28 | 2026-11-22 | E. Trade-ins | How should staff inspect submission photos and offers? | Enlarge the detail dialog and add a photo lightbox with keyboard navigation, zoom, and open in new tab. Show offer amount, status, and deadline. | Staff detail displayed thumbnail images without interactions, and the offer deadline from the API was absent from the dialog. |
| 29 | 2026-11-22 | F. Reviews | How should staff read a full review? | Make rows open a detail dialog with the complete review and Hide/Show actions. | The API already supplied the full review and moderation data, but the frontend only rendered a truncated list with isolated visibility actions. |
| 30 | 2026-11-22 | G. Enquiries | Who can view storefront enquiries and why did the inbox look empty? | Managers can see every enquiry. Sales executives and receptionists with Handles enquiries and module access can see all enquiries, including unassigned ones. | The frontend omitted /api/v1 and swallowed request failures as an empty list. The default backend query never excluded unassigned items. View-only access can read threads. Full access can assign, update, and reply. |
| 31 | 2026-11-22 | H. Email log | How should absent delivery configuration be recorded? | Record Skipped with Email provider not configured when the provider, API key, or sender is missing. Save genuine provider failures and support manager retries. | The previous code treated missing provider credentials as Failed and provider=none as Suppressed. The existing error_message column can store reasons, but the database status constraint excluded Skipped. In-app notifications use a separate row from the outbox. |
| 32 | 2026-11-22 | I. Staff and technicians | How should managers control staff access and maintain profiles? | Owner chose role presets as the access ceiling. Store module overrides, use a manager-only enquiry switch, and require temporary password changes. Add staff activity and technician profile details. | The switch targeted a URL the backend did not register. The staff view lacked complete add, edit, and detail flows, and the existing soft-delete endpoint did not protect manager accounts. Server dependencies enforce role and module access. Reset and deactivation revoke existing staff tokens. Work days, hours, and hourly rate are profile fields. Storefront booking retains the existing slot and booking-fee rules. |
| 33 | 2026-11-22 | J. Verification | How should the changes be tested and deployed? | Verify with SQLite regression tests, a separate local PostgreSQL cluster, and local frontend builds. The owner applies Alembic revision 0005_staff_portal to Neon. | A clean PostgreSQL upgrade exposed a pre-existing 0003 migration problem. Its status check lookup matched lead_status too. Narrowing it to the status column fixes fresh installs, while databases already at 0004 proceed with 0005. The full suite passed 144 tests. Chrome verified all nine reported staff pages, database-backed service job creation, the Reserved badge, review moderation, trade-in photo controls, and recovery from a render failure. |

## Constitution Articles Referenced

| Article | Summary | Where Applied |
|---|---|---|
| XI | All money as Decimal/NUMERIC, never float | All price, balance, amount, fee fields |
| XIII | Lock order: vehicle → reservation → bank_account | reserve, cancel, expire, complete-sale routes |
| XV | customer_id always from token, never from request body | All `/store/` endpoints |
| XVI | Password hashing via `app.core.security` (bcrypt) | Customer signup, login, seed scripts |
| XVII | All colors in Tailwind tokens only | Storefront uses custom CSS variables mapped to Tailwind |
| XVIII | Show "Demo project — no real money" note near payment | Bank page, reservation payment, service booking payment |
| XIX | Ambiguity rule — ask owner, never guess | All decisions above were reviewed |
